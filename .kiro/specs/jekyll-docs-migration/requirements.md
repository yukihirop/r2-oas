# Requirements Document

## イントロダクション

R2-OASプロジェクトのドキュメントサイトを、現在のDocsify形式からJekyll形式に移行します。この移行により、GitHub Pagesとのより良い統合、検索エンジン最適化(SEO)の改善、静的サイト生成による高速化とセキュリティ向上を実現します。

既存の `old_docs` ディレクトリには、Docsifyを使用した以下のドキュメントが含まれています:
- 使い方ガイド (16種類のUsageドキュメント)
- 設定ガイド (COC、Configure、CORS)
- スキーマ仕様 (OpenAPI 3.0.0)
- 注意事項とトラブルシューティング

これらのコンテンツを保持しつつ、Jekyll + GitHub Pagesに最適化された新しい `docs` ディレクトリとして再構築します。

## 要件

### 要件1: Jekyllプロジェクト構造の作成

**目的:** プロジェクト管理者として、標準的なJekyllプロジェクト構造を持つ `docs` ディレクトリを作成したい。これにより、GitHub Pagesで正しくビルドされ、メンテナンスしやすいドキュメントサイトを構築できるようにする。

#### 受入基準

1. WHEN ドキュメント移行プロセスが開始されたとき THEN Jekyllプロジェクトは `docs/` ディレクトリをルートとして作成されるべきである
2. WHEN Jekyll構造が作成されるとき THEN Jekyllプロジェクトは以下の標準ディレクトリを含むべきである:
   - `_layouts/` - レイアウトテンプレート
   - `_includes/` - 再利用可能なコンポーネント
   - `_sass/` - スタイルシート
   - `assets/` - 静的アセット (CSS、画像等)
   - `_config.yml` - Jekyll設定ファイル
3. WHEN `_config.yml` が作成されるとき THEN 設定ファイルは以下の設定を含むべきである:
   - `title: "R2-OAS Documentation"`
   - `description: "OpenAPI documentation generator for Rails"`
   - `baseurl: "/r2-oas"`
   - `url: "https://yukihirop.github.io"`
   - GitHub Pagesで動作するテーマ設定
4. WHEN Jekyll構造が完成したとき THEN `Gemfile` は Jekyll と GitHub Pages gem を含むべきである

### 要件2: コンテンツの移行とディレクトリ構造マッピング

**目的:** ドキュメント管理者として、`old_docs` の既存コンテンツを適切なJekyllディレクトリ構造にマッピングしたい。これにより、全てのドキュメントが論理的に整理され、ユーザーが情報を見つけやすくする。

#### 受入基準

1. WHEN コンテンツ移行が実行されるとき THEN Jekyllプロジェクトは以下のディレクトリマッピングを実施すべきである:
   - `old_docs/usage/*.md` → `docs/usage/` (使い方ガイド)
   - `old_docs/setting/*.md` → `docs/configuration/` (設定ガイド)
   - `old_docs/schema/*.md` → `docs/schema/` (スキーマ仕様)
   - `old_docs/attention/*.md` → `docs/guides/` (注意事項)
   - `old_docs/trableshouting/*.md` → `docs/troubleshooting/` (トラブルシューティング)
2. WHEN Markdownファイルが移行されるとき THEN 各ファイルはJekyll Front Matterを含むべきである:
   - `layout:` - 使用するレイアウト
   - `title:` - ページタイトル
   - `permalink:` - カスタムURL
   - `nav_order:` (オプション) - ナビゲーション順序
3. WHEN `old_docs/README.md` が処理されるとき THEN 内容は `docs/index.md` としてトップページに変換されるべきである
4. IF ドキュメントファイルが内部リンクを含む場合 THEN リンクはJekyllの `{{ site.baseurl }}` 構文を使用して更新されるべきである

### 要件3: ナビゲーション構造の構築

**目的:** ドキュメント閲覧者として、直感的で階層的なナビゲーションを使用してドキュメント内を移動したい。これにより、必要な情報に素早くアクセスできるようにする。

#### 受入基準

1. WHEN ナビゲーションが構築されるとき THEN Jekyllサイトは以下の主要セクションを含むべきである:
   - Getting Started (はじめに)
   - Usage (使い方)
   - Configuration (設定)
   - Schema Reference (スキーマリファレンス)
   - Troubleshooting (トラブルシューティング)
   - Guides (ガイド)
2. WHEN サイドバーナビゲーションが生成されるとき THEN `old_docs/_sidebar.md` の構造を参照して、階層的なナビゲーションを実装すべきである
3. WHEN ユーザーがページを閲覧しているとき THEN ナビゲーションは現在のページをハイライト表示すべきである
4. IF ページが特定のセクションに属する場合 THEN そのセクションの親項目は展開された状態で表示されるべきである

### 要件4: レイアウトとテーマの実装

**目的:** プロジェクト管理者として、R2-OASブランドに沿った一貫性のあるデザインを持つドキュメントサイトを提供したい。これにより、プロフェッショナルで読みやすいドキュメント体験を実現する。

#### 受入基準

1. WHEN レイアウトが作成されるとき THEN 以下のレイアウトファイルが実装されるべきである:
   - `_layouts/default.html` - 基本レイアウト
   - `_layouts/page.html` - 標準ページレイアウト
   - `_layouts/home.html` - トップページレイアウト
2. WHEN デフォルトレイアウトが適用されるとき THEN レイアウトは以下の要素を含むべきである:
   - ヘッダー (サイトタイトル、GitHubリンク)
   - サイドバーナビゲーション
   - メインコンテンツエリア
   - フッター
3. WHEN スタイリングが実装されるとき THEN サイトはレスポンシブデザインを採用し、モバイルデバイスでも適切に表示されるべきである
4. WHEN コードブロックが表示されるとき THEN シンタックスハイライトが適用され、Ruby、Bash、YAML、JSON形式をサポートすべきである

### 要件5: 検索機能の実装

**目的:** ドキュメント利用者として、キーワード検索を使用して関連ドキュメントを素早く見つけたい。これにより、大量のドキュメントの中から必要な情報に効率的にアクセスできるようにする。

#### 受入基準

1. WHEN 検索機能が実装されるとき THEN Jekyllサイトはクライアントサイド検索 (例: Lunr.js) またはサーバーサイド検索を統合すべきである
2. WHEN ユーザーが検索ボックスに入力したとき THEN システムは入力に応じてリアルタイムで検索結果を表示すべきである
3. WHEN 検索結果が表示されるとき THEN 結果は以下の情報を含むべきである:
   - ページタイトル
   - マッチした文脈のスニペット
   - ページへのリンク
4. IF 検索クエリがマッチしない場合 THEN システムは「結果が見つかりませんでした」というメッセージを表示すべきである

### 要件6: Markdown拡張機能のサポート

**目的:** ドキュメント作成者として、拡張されたMarkdown機能を使用してリッチなコンテンツを作成したい。これにより、表現力のあるドキュメントを効率的に作成できるようにする。

#### 受入基準

1. WHEN Markdownが処理されるとき THEN Jekyllは GitHub Flavored Markdown (GFM) をサポートすべきである
2. WHEN ドキュメントにテーブルが含まれるとき THEN GFMテーブル構文が正しくレンダリングされるべきである
3. WHEN ドキュメントにコードブロックが含まれるとき THEN 言語指定付きのシンタックスハイライトが適用されるべきである
4. WHEN ドキュメントにアラートや注意書きが必要なとき THEN カスタムLiquidタグまたはincludeを使用して、情報ボックス（info、warning、danger）を表示できるべきである
5. WHEN 外部リンクが含まれるとき THEN リンクは `target="_blank"` 属性を持ち、新しいタブで開かれるべきである

### 要件7: GitHub Pagesへのデプロイ設定

**目的:** プロジェクト管理者として、Jekyll docsディレクトリがGitHub Pagesで自動的にビルドおよび公開されるようにしたい。これにより、ドキュメント更新時の手動デプロイ作業を不要にする。

#### 受入基準

1. WHEN リポジトリ設定が構成されるとき THEN GitHub Pagesのソースは `/docs` ディレクトリに設定されるべきである
2. WHEN `docs/_config.yml` が作成されるとき THEN 設定ファイルはGitHub Pagesの制約を考慮した設定を含むべきである:
   - 許可されたプラグインのみ使用
   - 適切な `baseurl` と `url` 設定
3. WHEN docsディレクトリの変更がmasterブランチにプッシュされたとき THEN GitHub Pagesは自動的にサイトをリビルドして公開すべきである
4. WHEN ビルドエラーが発生した場合 THEN GitHub Pagesはビルドエラーをリポジトリ管理者に通知すべきである
5. IF `.nojekyll` ファイルが存在する場合 THEN ファイルは `docs/` ディレクトリから削除され、Jekyllビルドが有効化されるべきである

### 要件8: コンテンツの整合性とバリデーション

**目的:** 品質保証担当者として、移行されたドキュメントが元のコンテンツと一貫性があり、すべてのリンクが機能することを確認したい。これにより、ユーザーにとって信頼性の高いドキュメントを提供する。

#### 受入基準

1. WHEN コンテンツ移行が完了したとき THEN 移行プロセスは全ての `.md` ファイルが正常に移行されたことを検証すべきである
2. WHEN ドキュメントがビルドされたとき THEN システムは内部リンク切れを検出して報告すべきである
3. WHEN 移行後のドキュメントが確認されるとき THEN 各ページのコンテンツは元の `old_docs` のコンテンツと意味的に一致すべきである
4. WHEN コードサンプルが移行されるとき THEN コマンド、パス、設定例は正確に保持されるべきである
5. IF 画像やアセットへの参照が存在する場合 THEN 参照は新しいディレクトリ構造に合わせて更新され、正しく表示されるべきである

### 要件9: メタデータとSEO最適化

**目的:** マーケティング担当者として、検索エンジンでドキュメントが適切にインデックスされ、検索結果で見つけやすくなるようにしたい。これにより、R2-OASの認知度と採用を促進する。

#### 受入基準

1. WHEN 各ページが生成されるとき THEN HTMLヘッダーは以下のメタタグを含むべきである:
   - `<title>` - ページタイトルとサイト名
   - `<meta name="description">` - ページ説明
   - `<meta property="og:title">` - Open Graphタイトル
   - `<meta property="og:description">` - Open Graph説明
   - `<meta property="og:type" content="website">`
2. WHEN サイトマップが生成されるとき THEN Jekyll-sitemap プラグインを使用して `sitemap.xml` が自動生成されるべきである
3. WHEN robots.txt が作成されるとき THEN ファイルは検索エンジンクローラーに対して適切なクロール指示を提供すべきである
4. WHEN ページURLが設定されるとき THEN URLは人間が読みやすく、SEOフレンドリーな構造 (例: `/usage/generate-docs/`) であるべきである

### 要件10: ドキュメント保守性とプロセス改善

**目的:** ドキュメント管理者として、将来的なドキュメント更新と保守を容易にするための仕組みを確立したい。これにより、長期的にドキュメント品質を維持できるようにする。

#### 受入基準

1. WHEN 新しいドキュメントページが追加されるとき THEN 開発者は標準的なFront Matterテンプレートを参照できるべきである
2. WHEN ドキュメントが更新されるとき THEN `_config.yml` の `last_updated` 設定またはGit履歴を使用して、最終更新日が自動的に表示されるべきである
3. WHEN ビルドプロセスが実行されるとき THEN ローカル開発環境で `bundle exec jekyll serve` コマンドを使用してプレビューできるべきである
4. WHEN 移行が完了したとき THEN プロジェクトは以下のドキュメントを含むべきである:
   - `docs/README.md` または `CONTRIBUTING.md` - ドキュメント貢献ガイド
   - ディレクトリ構造の説明
   - Front Matter使用例
5. IF ドキュメント構造に変更が必要な場合 THEN 変更は `_config.yml` または `_data/navigation.yml` で集中管理できるべきである
